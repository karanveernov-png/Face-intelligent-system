📁 The File Map — what every file does

start here

The project is two halves — a React dashboard (what you see) and a FastAPI backend (the brain that runs the models). Models live as .onnx files on disk; nothing talks to the internet.

Backend — the brain (backend/app/)

backend/app/main.py
entry point

Creates the FastAPI app. Adds security headers, request logging, rate limiting, CORS. On startup it checks the encryption key and (in production) verifies model file hashes. Serves /health and /ready. Starts by loading no models — each service loads its own lazily on first use.

backend/app/api/routes.py
REST endpoints

The HTTP surface: /api/models/status, /api/analyze/image, /api/analyze/video, /api/faces/enroll, list/delete/withdraw-consent. Thin wrappers — they validate the upload, open it with OpenCV, and hand off to the pipeline.

backend/app/api/ws.py
live webcam

WebSocket at /ws/analyze. Receives raw JPEG frames from the browser, decodes them, runs the pipeline in a thread, sends JSON back per frame. Also enforces origin checks, connection limits (10/IP, 100 total), size cap (8 MB/frame) and a 5-min idle timeout.

backend/app/services/pipeline.py
the orchestrator ⭐

The heart. analyze_image() does: detect faces → de-duplicate overlapping boxes → crop → optionally run recognition / expression / age → temporal smoothing. Each stage is wrapped in try/except so one failing model doesn't kill the whole result.

backend/app/services/detection.py
find the faces

Runs SCRFD-10G INT8 via ONNX Runtime, decodes the raw multi-scale outputs into boxes + 5 landmarks, applies NMS. Returns DetectedFace objects that already carry the cropped pixels.

backend/app/services/recognition.py
who is this?

align_face() warps the face to 112×112 using the 5 landmarks. _embed_batch() turns aligned crops into 512-D vectors with ArcFace-R50. Enroll / list / delete / withdraw-consent and the on-disk embeddings/index.json all live here.

backend/app/services/expressions.py
mood labels

HSEmotion ENet-B0-8 gives 8 probabilities per face. Anything below 0.22 confidence is reported as "uncertain" rather than pretending to know.

backend/app/services/age_estimation.py
age + gender

Two independent models (InsightFace genderage + FairFace). Averages their age estimates; the disagreement between them becomes the reported uncertainty. No heuristics, no guesses.

backend/app/services/tracking.py
memory across frames

FaceTracker keeps track IDs alive between frames using IoU matching, predicts box positions with Lucas–Kanade optical flow, and EMA-smooths expression/age so labels stop flickering.

backend/app/core/onnx_runtime.py
model plumbing

The only place ONNX sessions are created. Picks OpenVINO → CPU execution providers, sets thread pools, auto-quantizes FP32 → INT8 once and caches it, and builds batch tensors with cv2.dnn.blobFromImages.

backend/app/core/config.py
all settings

Every knob: model filenames, thresholds (detection 0.5, recognition 0.68), frame skip, detection interval, upload limits, consent/retention rules. Read from env vars or a .env file.

backend/app/security/*.py
4 small guards

validation.py rejects bad/oversized/decompression-bomb uploads safely. crypto.py AES-256-GCM encryption of embeddings. auth.py API keys + roles (admin/operator/viewer). model_integrity.py verifies model file hashes in production.

backend/app/schemas/models.py
response shapes

Pydantic models defining what the API returns (model status, enrolled entries, delete/consent responses).

backend/scripts/download_models.py
fetch weights

Downloads the upstream ONNX weights, quantizes them to INT8 and writes them into models/. Models are not in git because of size/licensing.

backend/tests/
safe checks

Pytest suite using synthetic images — verifies plumbing, validation, cosine math, alignment behaviour. Proves the wiring works, not the accuracy on real faces.

services/api.ts

services/webcam.ts

🔍 Step 1 — Face Detection (SCRFD)

required

Question it answers: "Where are the faces?" A detector has no idea who anyone is.

What's actually happening

  1. The image is letterboxed into a 640×640 square (aspect ratio preserved, padded with black).
  2. Its pixels are turned into a tensor with cv2.dnn.blobFromImage: scaled by 1/128, mean 127.5, and BGR swapped to RGB.
  3. SCRFD outputs, at three stride levels (8, 16, 32), a score per anchor plus box-offset and 5-landmark-offset predictions.
  4. Offsets are decoded back into real pixel coordinates, then divided by the letterbox scale to return to the original image space.
  5. Non-Maximum Suppression (NMS, IoU 0.4) collapses duplicate boxes into one per face.
// What detection returns per face
{
  "bbox": {"x": 100, "y": 120, "w": 200, "h": 200},   // top-left + width/height
  "confidence": 0.97,
  "landmarks": {
    "left_eye":   [130, 180], "right_eye": [330, 175],
    "nose":       [215, 220],
    "mouth_left": [150, 260], "mouth_right": [330, 255]
  },
  "crop_bgr": <face pixels>
}

The threshold trade-off is real: lower detection_confidence_threshold (default 0.5) → more boxes, more false positives. Raise it → fewer false positives, but real faces get dropped. No value eliminates both. That's fundamental, not a bug.

📐 Step 2 — Alignment (5-point Umeyama transform)

critical

Why it exists: ArcFace was trained on faces where the eyes, nose and mouth sit at fixed positions. If you feed it a tilted crop, the embedding comes out different — even for the same person.

The canonical template (112×112)

These five coordinates are the ones the ArcFace weights were trained against:

Pointxy
Left eye38.294651.6963
Right eye73.531851.5014
Nose56.025271.7366
Mouth left41.549392.3655
Mouth right70.729992.2041

The three tiers (fallbacks matter)

  1. 5-point similarity transform — cv2.estimateAffinePartial2D(src, dst, method=LMEDS) then cv2.warpAffine(..., (112,112)). Rotation + uniform scale + translation. Best case.
  2. 2-point eye-line rotation — rotate around the eye midpoint so the eyes are horizontal, then slice the box out of the rotated frame. Used when only the eyes were found.
  3. Plain crop — no landmarks at all; just use the box. Accuracy drops, but it never crashes.
Golden rule: enrollment and matching must use the same alignment. An embedding from an aligned face is not comparable to one from a raw crop. Mismatch silently degrades accuracy without any error.

🧠 Step 3 — Recognition (ArcFace embeddings)

core

Question it answers: "Is this one of the people enrolled on this machine?"

What an embedding is

512 floating-point numbers — a coordinate in a 512-dimensional space. Same person, different photos → nearby points. Different people → far apart. It's a fingerprint made of math.

aligned = align_face(image, face)            # 112×112, canonical pose
emb     = arcface(aligned)                   # shape (512,), L2-normalised
dist    = 1 - dot(emb, enrolled_emb)         # cosine distance: 0 = identical

The matching loop

  1. Compute the query embedding.
  2. Compute distance to every enrolled embedding (one matrix multiply for all).
  3. Take the smallest distance.
  4. If it's ≤ recognition_distance_threshold (0.68) → return that name.
  5. Else → return "Unknown". Never return the nearest name regardless.

Cosine distance cheat-sheet: 0 = identical direction · 1 = perpendicular (unrelated) · 2 = opposite.

Why "Unknown" must exist: an embedding model always outputs some vector, even for a stranger. Without a threshold, every stranger would be "the closest enrolled person". The threshold is what turns "nearest guess" into "a real match or nobody".
One known gotcha in this codebase: w600k_r50_int8.onnx accepts a dynamic input batch but its output is hard-coded to [1, 512]. So batching multiple faces through it silently mixes rows. The code detects this and loops one-by-one. Never trust "dynamic input" to mean "dynamic output".

😊 Step 4 — Expression classification

optional

HSEmotion (EfficientNet-B0, 8 classes) outputs one probability per class. Results are probabilities of visible facial configuration — not measurements of feelings.

The 8 classes

angry

lowered brows, tightened lips

contempt

one-sided lip raise

disgust

nose wrinkle, upper-lip curl

fear

raised brows, widened eyes

happy

lifted cheek, lip corners up

neutral

relaxed, no strong action

sad

inner brow raise, lip corners down

surprise

brows raised, jaw dropped

{ "label": "happy", "certain": true,
  "scores": { "angry":0.02, "happy":0.87, "neutral":0.05, ... },
  "note": "Visual classification only — not a measurement of internal state." }

Uncertainty rule: if the top score is below 0.22, the label becomes "uncertain" and certain:false — the system openly says it doesn't know.

Temporal EMA (video/webcam only): scores are blended with the previous frame's scores at α = 0.4 and re-normalised. That's what stops the label flickering between happy/neutral 30 times a second.

Limitations: drops sharply under occlusion (masks, hands), extreme pose, low light. Never use for employment, eligibility, policing or any decision about a person.

👤 Step 5 — Age & Gender (two-model ensemble)

optional

Two models that were trained independently disagree in useful ways. The system averages them and reports the disagreement itself as uncertainty, instead of picking a confident number.

Face crop
GenderAge (96×96)direct continuous age 0–100 + 2 gender logits · ~1.3 MB
FairFace (224×224)9 age buckets (0-2 … 70+) → expected value over bucket midpoints · ~21 MB INT8
age      = (genderage_age + fairface_age) / 2
uncert   = 6.0 + 0.5 * abs(genderage_age - fairface_age)   # years
bucket   = _bucket_for_age(round(age))   # "0-2" … "60-100"

Age buckets

0-2 · 4-6 · 8-12 · 15-20 · 25-32 · 38-43 · 48-53 · 60-100

Gender

GenderAge emits two logits, [female, male]. The larger one wins, and its softmax probability is reported as gender_confidence.

Design principle worth copying: an earlier version used heuristics ("smooth skin ⇒ child", "facial hair ⇒ male", otherwise default to adult 20–25). That is backwards — ambiguous should stay ambiguous. The current code has no such branch: every face gets identical treatment, and an unreadable face is returned as unusable rather than as a confident-looking placeholder.

👥 Step 6 — Tracking across frames

video/webcam

Detection ≠ tracking. The detector has no memory. Tracking stitches boxes across frames into stable identities and enables the performance shortcuts.

Three mechanisms inside FaceTracker

  1. IoU matching — new box overlaps an old track's box by ≥ 0.3? Same track, keep its ID. Otherwise mint a new ID.
  2. Optical flow between detections — full SCRFD runs only every 3rd frame (detection_interval=3). In-between frames use Lucas–Kanade on a 4×4 point grid inside the box, take the median shift, and move the box. If the region is flat/low-texture, keep the last velocity. A track unconfirmed for more than 2 predicted frames stops being drawn (kills "ghost" boxes).
  3. EMA smoothing — expression scores and age are blended per track (α = 0.4) so labels stay steady.
# per-track state
track_id, box, velocity, missed_frames, age_frames,
ema_expression_scores, ema_age, unconfirmed_predict_frames,
5 landmark points (shifted along with the box)

Lifecycle: a track lives until it has missed more than tracker_max_missed_frames (4) detection cycles, then it's deleted.

De-duplication safety net

After detection the pipeline also drops any two boxes overlapping ≥ 0.45. Two genuinely distinct faces practically never overlap that much — so that's tracker drift or detector noise, and it gets removed.

Tooling vocabulary

OpenCV (cv2)

Image/video I/O, resize, warp, colour conversion, NMS, blob building, optical flow. The "hands".

ONNX

An open file format for trained neural networks. Framework-independent.

ONNX Runtime

The engine that executes .onnx files efficiently on your CPU (or OpenVINO/NPU). The "calculator".

INT8 quantization

Storing weights as 8-bit ints instead of 32-bit floats. ~4× smaller, usually faster, minimal accuracy loss.

NCHW blob

Tensor layout models expect: batch, channels, height, width. Built by cv2.dnn.blobFromImages.

Softmax

Turns raw scores into probabilities that sum to 1.

Cosine distance

1 − dot(a,b) for unit vectors. Distance between two face "fingerprints".

IoU

Overlap ÷ union of two boxes. Used for NMS, tracking and de-duplication.

EMA

Exponential moving average — blends new value with old, smoothing video output.

Umeyama / affine

The family of transforms that rotate+scale+shift points onto a template.

BGR vs RGB

OpenCV loads BGR; most models want RGB. The #1 silent bug source.

NMS

Non-Maximum Suppression — keeps the best box when several overlap.

🔒 Security, privacy & consent

important

Where data lives

data/
├── embeddings/index.json   enrolled people (name, model, consent, embedding)
├── gallery/                optional kept enrollment images (off by default)
└── tmp_uploads/            uploads — deleted right after each request

Guarantees in this codebase

  • Consent gate: enrollment without consent_confirmed=true returns 403. Consent version is recorded.
  • Only embeddings stored: the original photo is discarded unless retain_enrollment_images is turned on.
  • Withdraw consent: POST /api/faces/{id}/withdraw-consent permanently deletes the embedding and any kept image.
  • Encryption at rest: if FACE_ENCRYPTION_KEY + FACE_ENCRYPTION_SALT are set, embeddings are sealed with AES-256-GCM (PBKDF2-derived key, 100k iterations). Key rotation is supported.
  • Upload hardening: extension whitelist, 25 MB cap, decompression-bomb check on decoded dimensions, random server-side filenames (no path traversal).
  • Rate limiting (slowapi, 60 rpm default), CORS origin allowlist, security headers, request IDs, no stack traces leaked in production.
  • Model integrity: in production, model file hashes are verified at startup.
Never commit FACE_ENCRYPTION_KEY / FACE_ENCRYPTION_SALT. Generate with: python -c "import secrets,base64;print(base64.b64encode(secrets.token_bytes(32)).decode())"

Ethical limits stated by the project itself

Recognition, expressions and age/gender are probabilistic outputs — not proof of identity, not measured emotion, not verified age. They must not drive decisions about employment, eligibility, access control, law enforcement or safety.

❓ Top 10 Questions Tech Developers Ask (Hackathon Edition)

q&a
Q1. Do I need a GPU?
No. Everything runs on CPU via ONNX Runtime with OpenVINO fallback. The models are INT8-quantized (~70 MB total), so a laptop CPU handles images fine (~1–1.2 s per image with all tasks on). Real-time webcam needs frame-skipping (every 3rd frame) to stay smooth.
Q2. Is it free / no API keys?
Yes. All models are local ONNX weights. No cloud, no API keys, no telemetry, no internet needed after downloading the models once.
Q3. How does recognition actually work?
SCRFD finds the face → 5 landmarks align it to 112×112 → ArcFace-R50 outputs a 512-D vector → cosine distance to every enrolled person → nearest under 0.68 is a match, otherwise "Unknown". Never force a match.
Q4. What are "Unknown" results?
A face that doesn't clear the 0.68 cosine threshold against anyone enrolled. It's a valid result — don't force-match strangers.
Q5. Can I use this for attendance / access control?
Not recommended as the sole decision. It's probabilistic. The project's own responsible-use docs say outputs must not drive employment, eligibility, law enforcement, or safety decisions. Always add human oversight.
Q6. Is consent required?
Yes for enrollment. `consent_confirmed=true` must be sent, or the API returns 403. Embeddings can be withdrawn (deleted) anytime via `/api/faces/{id}/withdraw-consent`.
Q7. How accurate are age & gender?
It's an ensemble of GenderAge + FairFace. The system averages them and reports uncertainty based on how much they disagree. Treat it as approximate, never as verified age or medical fact.
Q8. Why are expressions sometimes wrong?
HSEmotion classifies visible facial configuration (8 classes). Accuracy drops with masks, side angles, low light. Below 0.22 confidence it says "uncertain" instead of guessing.
Q9. Where is biometric data stored?
Locally under `./data/`: `embeddings/index.json` (512-D vectors + consent metadata), optional `gallery/` images, `tmp_uploads/` (auto-deleted). Can be encrypted with AES-256-GCM via `FACE_ENCRYPTION_KEY`.
Q10. What breaks this?
BGR vs RGB mixups, wrong normalization, missing consent, decompression-bomb images, mismatched alignment between enroll and query, and models not provisioned (`download_models.py`).
Hackathon tip: Demo the webcam tab first (instant "wow"), then enroll a teammate and show recognition on a second photo. Mention "local-first, no API keys, consent-based" — judges love privacy-by-design.

The five mental models to keep

1. An image is a grid of numbers

3 channels × height × width, uint8 0–255. Everything else is math on that grid.

2. Detection ≠ recognition

Finding a face and naming a face are two different models with two different jobs.

3. Alignment makes faces comparable

Same person, different angle = different embedding unless you align first.

4. Every model has a threshold

Thresholds trade false positives against false negatives. There is no perfect value.

5. Uncertainty is information

"uncertain", wide age bands and "Unknown" are honest outputs — not bugs.
